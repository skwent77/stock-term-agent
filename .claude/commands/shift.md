# SHIFT: ChromaDB 기반 LangChain 프로젝트 TDD 지시문

이 프로젝트를 한 번에 크게 구현하지 말고, 아래 원칙과 순서에 따라 **작은 수직 단위(vertical slice)**로 완성해줘.

## 현재 프로젝트 목표

공신력 있는 출처를 바탕으로 구축한 한국어 주식 용어 데이터를 임베딩하여 ChromaDB에 저장하고, LangChain 에이전트가 사용자의 질문에 따라 검색 도구를 호출한 뒤 GPT 또는 Claude로 근거 있는 설명을 생성하는 AI 투자교육 서비스를 구축한다.

현재 핵심 구조는 다음 책임 경계를 따른다.

```text
stock_terms.json
  → Pydantic 데이터 계약·품질검증
    → LangChain Document 변환
      → Embedding Model
        → ChromaDB
          → Retriever/Search Service
            → LangChain create_agent
              → GPT 또는 Claude
```

웹 기능을 추가하면 다음 구조를 사용한다.

```text
Web UI
  → FastAPI
    → Application Service
      → LangChain Agent
        → Python Tools
          → ChromaDB
```

- Pydantic: 원천 JSON의 구조, 타입, 필수값과 출처 검증
- LangChain Document: 임베딩할 본문과 검색·필터링용 메타데이터 구성
- Embedding Model: 한국어 주식 용어를 벡터로 변환
- ChromaDB: 벡터, 문서와 메타데이터를 영속 저장하고 유사도 검색
- Python Tool: 금융 용어 검색 기능을 에이전트에 제공
- LangChain `create_agent`: GPT 또는 Claude가 필요한 도구를 선택·호출
- FastAPI: 웹 요청 검증과 에이전트 호출 경계 제공
- LLM: 검색 결과를 자연어로 설명하며 출처 없는 금융 사실을 만들지 않음

PostgreSQL, MCP와 pandas ETL은 현재 핵심 범위에 포함하지 않는다. 실제 요구가 생기기 전에는 추가하지 않는다.

## 필수 작업 방식

모든 기능은 다음 TDD 사이클을 지켜 구현한다.

1. 현재 코드와 테스트를 읽고 변경 범위를 한 문장으로 정의한다.
2. 기대 동작과 실패 조건을 나타내는 테스트를 먼저 작성한다.
3. 새 테스트가 의도한 이유로 실패하는지 실행하여 확인한다. 기존 테스트 실패와 구분한다.
4. 해당 테스트만 통과시키는 최소한의 운영 코드를 구현한다.
5. 관련 테스트와 전체 테스트를 실행한다.
6. 테스트가 통과한 상태에서만 중복 제거, 이름 개선, 책임 분리 등의 리팩터링을 수행한다.
7. 전체 테스트를 다시 실행하고 구현 결과와 다음 작업을 짧게 기록한다.

테스트를 작성한 직후 곧바로 구현하지 말고 반드시 **실패하는 테스트(Red)**를 먼저 확인한다. 테스트가 처음부터 통과한다면 테스트가 기존 동작과 무엇을 다르게 검증해야 하는지 재검토한다.

## 구현 순서

아래 단계를 건너뛰거나 여러 단계를 한꺼번에 섞지 않는다. 각 단계는 실행 가능한 결과물과 테스트를 남긴 뒤 다음 단계로 이동한다.

### 1. 금융 용어 데이터 계약과 품질검증

- `stock_terms.json`을 직접 구축한 원천 시드 데이터로 취급한다.
- Pydantic 모델로 용어와 출처의 데이터 계약을 정의한다.
- 용어 ID, 한글명, 영문명, 약어, 별칭, 카테고리, 정의, 예시, 주의사항, 출처, 수집일, 검증일과 버전을 표현한다.
- Pydantic으로 필수값, 타입, 문자열 정규화, 허용된 카테고리와 출처 URL을 검증한다.
- 데이터셋 단위 검사에서는 ID·한글명·영문명·별칭 중복과 지나치게 짧은 정의를 확인한다.
- 검증 결과에는 전체·통과·제외 레코드 수와 제외 사유를 포함한다.
- LLM은 표현 초안에만 사용할 수 있으며, 검증되지 않은 생성 결과를 자동 저장하지 않는다.

### 2. LangChain Document 변환

- 검증을 통과한 용어 하나를 `Document` 하나로 변환한다.
- 용어 데이터가 짧으므로 근거 없는 text splitting이나 chunking을 추가하지 않는다.
- `page_content`에는 한글명, 영문명, 약어, 별칭, 정의, 예시와 주의사항처럼 의미 검색에 필요한 내용을 포함한다.
- `metadata`에는 term_id, 대표 용어, 카테고리, 출처명, 출처 URL과 버전처럼 필터링·추적에 필요한 스칼라 값만 저장한다.
- 리스트와 중첩 객체를 Chroma metadata에 직접 넣지 않는다.
- 동일 입력이 항상 동일한 Document ID와 내용을 만드는지 테스트한다.

### 3. ChromaDB 인덱싱

- Chroma 접근 코드를 Document 변환 및 에이전트 코드와 분리한다.
- collection 이름과 데이터 버전을 명시한다.
- `term_id`를 안정적인 Document ID로 사용한다.
- 같은 데이터를 반복 인덱싱해도 중복 벡터가 생기지 않도록 upsert 또는 동등한 멱등 동작을 구현한다.
- 삭제된 용어와 변경된 용어의 동기화 정책을 코드와 문서에 명시한다.
- 테스트에서는 실제 외부 임베딩 모델 대신 결정적인 fake embedding과 임시 디렉터리를 사용한다.
- 첫 인덱싱, 반복 인덱싱, 수정 반영, 빈 데이터, 잘못된 metadata와 저장소 재로딩을 테스트한다.

### 4. 검색 및 Retriever 서비스

- 정확 용어 조회와 의미 기반 검색의 책임을 구분한다.
- top_k 범위, 최소 관련도 기준과 선택적인 카테고리 필터를 검증한다.
- 검색 결과에는 문서 본문뿐 아니라 점수, 용어 ID, 카테고리와 출처를 포함한다.
- 검색 결과 없음, 낮은 관련도, 동점 결과와 저장소 오류를 테스트한다.
- 검색 품질 평가는 대표 질문과 기대 용어로 구성한 작은 고정 평가셋을 별도로 둔다.

### 5. LangChain 도구

- `search_stock_terms`, `get_stock_term`, `list_categories`처럼 역할이 명확한 Python 도구를 제공한다.
- 도구의 이름, 설명, 입력 스키마만 보고 모델이 올바른 도구를 선택할 수 있게 작성한다.
- 도구 함수에는 LLM 호출을 넣지 않고 검색 서비스만 호출한다.
- 정상 조회, 결과 없음, 잘못된 입력과 내부 검색 오류를 구조화된 결과로 반환하는지 테스트한다.
- 도구 결과에는 근거 출처를 유지한다.

### 6. ReAct형 LangChain 에이전트

- deprecated된 `langgraph.prebuilt.create_react_agent`를 사용하지 않는다.
- 현재 권장 API인 `from langchain.agents import create_agent`를 사용한다.
- GPT와 Claude 모델 선택을 설정으로 분리한다.
- 모델이 도구 결과 없이 용어 정의나 금융 수치를 지어내지 않도록 system prompt를 작성한다.
- 정상 도구 선택, 불필요한 도구 호출 방지, 도구 오류, 최대 반복 횟수와 타임아웃을 테스트한다.
- 에이전트 테스트는 실제 API 호출 대신 fake model, 고정 응답 또는 기록된 fixture를 우선 사용한다.
- 사용자에게 숨겨진 사고 과정을 노출하지 않고 호출한 도구, 입력, 결과 출처만 관찰 가능하게 기록한다.

### 7. RAG 답변 품질과 모델 공급자

- 검색된 문맥과 출처를 답변 프롬프트에 명확하게 전달한다.
- 근거가 없으면 모른다고 답하고 추가 검색이 필요함을 알린다.
- 답변에 사용된 용어와 출처를 사용자에게 표시한다.
- GPT와 Claude의 응답 형식을 공통 애플리케이션 인터페이스로 감싼다.
- API 키는 환경변수로만 주입하고 코드, 이미지와 로그에 노출하지 않는다.
- rate limit, timeout, 모델 오류와 빈 응답을 테스트한다.

### 8. FastAPI와 웹 UI

- 핵심 검색·에이전트 단계가 완료된 후 `/health`, `/terms/search`, `/chat`을 작은 단위로 추가한다.
- Pydantic 요청·응답 모델을 사용하고 HTTP 계층에 검색·임베딩 로직을 넣지 않는다.
- 외부 모델 호출과 검색 서비스는 dependency override가 가능한 구조로 만든다.
- 정상 요청, 잘못된 입력, 검색 결과 없음과 서비스 오류의 상태 코드를 테스트한다.
- 웹 UI에는 사용자 질문, AI 답변, 호출된 도구와 데이터 출처를 보여준다.
- FastAPI는 실제 웹 소비자가 생겼을 때만 유지하고 Swagger를 보여주기 위한 장식으로 추가하지 않는다.

### 9. 선택적 포트폴리오·시장 데이터 확장

- 핵심 주식 용어 RAG가 테스트와 문서까지 완성된 후에만 진행한다.
- SerpApi Google Finance를 사용할 경우 `MarketDataProvider` 인터페이스 뒤에 격리한다.
- 시세, 뉴스와 포트폴리오 계산을 ChromaDB 용어 저장소의 책임과 섞지 않는다.
- 현재가, 평균단가, 수익률과 보유 비중은 Python 도메인 코드에서 결정적으로 계산한다.
- 뉴스와 가격 변동의 시간적 연관성은 설명할 수 있지만 인과관계로 단정하지 않는다.
- API 할당량을 보호하기 위한 캐시, 타임아웃과 오류 정책을 테스트한다.

### 10. 컨테이너와 공개 저장소

- Docker 이미지에는 애플리케이션 실행에 필요한 파일만 포함한다.
- Chroma 영속 디렉터리는 개발 캐시와 배포 데이터의 정책을 구분한다.
- health check, 환경변수, 비루트 실행과 graceful shutdown을 검토한다.
- 운영 이미지에는 개발용 reload 옵션을 사용하지 않는다.
- `.env`, `.claude/settings.local.json`, 인증 JSON, Chroma 로컬 데이터와 각종 캐시를 Git에 포함하지 않는다.
- README에는 문제 정의, 데이터 구축 과정, 아키텍처, TDD 근거, 실행법, 검색 평가 결과와 기술 선택의 이유를 작성한다.

## 설계 및 품질 원칙

- 기존 사용자 변경사항을 보존하고 관련 없는 파일을 수정하지 않는다.
- 기능을 추가하기 전에 기존 인터페이스와 테스트 관례를 확인한다.
- 모듈은 데이터 계약, Document 변환, Chroma 저장, 검색, LangChain 도구, 모델 호출과 HTTP 책임을 섞지 않는다.
- 튜토리얼 코드를 그대로 복사하지 말고 현재 데이터와 요구에 맞춘 선택의 근거를 남긴다.
- 테스트를 통과시키기 위한 하드코딩이나 실제 오류를 숨기는 넓은 예외 처리를 하지 않는다.
- 임베딩, 네트워크, 시간과 LLM 응답처럼 비결정적인 의존성은 테스트에서 격리한다.
- 금융 데이터와 검색 결과에는 값뿐 아니라 출처와 데이터 버전을 포함한다.
- 벡터 검색 결과는 사실 확인의 근거이지 투자 권유나 인과관계의 증명이 아님을 명시한다.
- API 또는 원천 데이터의 이용약관과 재배포 제한을 문서화한다.
- 새 의존성을 추가할 때는 표준 라이브러리나 기존 의존성으로 해결할 수 없는 이유를 설명한다.

## 각 단계 완료 보고 형식

각 TDD 사이클이 끝날 때 다음 형식으로 간결하게 보고한다.

```text
작업 단위:
Red: 추가한 테스트와 확인한 실패 원인
Green: 최소 구현 내용
Refactor: 구조 개선 내용
검증: 실행한 명령과 결과
변경 파일:
다음 작업:
```

모호한 부분은 저장소와 기존 테스트에서 먼저 확인한다. 안전하고 범위가 작은 선택은 합리적으로 결정해서 계속 진행하고, 데이터 계약, 임베딩 모델, 외부 서비스처럼 결과를 크게 바꾸는 결정만 사용자에게 질문한다.
